# Savings benchmark, 2026-11-14

Spec §17 Test 5 and [issue #3](https://github.com/josephcake/soot/issues/3): run the same
workload with one expensive model and with soot's per-task routing, and measure cost, time,
success and retries. Raw data: [`2026-11-14.json`](2026-11-14.json). Script:
[`scripts/benchmark.mjs`](../../scripts/benchmark.mjs). Acceptance runs from the same day:
[`2026-11-14-acceptance.md`](2026-11-14-acceptance.md).

## Result in one paragraph

On the four prompts where both arms passed every run (10 paired runs with known cost),
routed runs cost **$0.0174** and baseline runs cost **$0.1176**. That is 85% less, at
provider-reported tokens times list prices. Across all 36 runs, routed passed **15/18** and
the baseline passed **11/18**. One prompt failed in both arms every time, and one prompt
favours routing for a reason that has nothing to do with model price (both explained below).
This is a small sample: two vendors, six prompts, three repetitions, one day.

## Method

- **Task set:** six prompts on [`examples/bench-app`](../../examples/bench-app), seven
  tasks. Each prompt is decomposed by a recorded fixture (`examples/bench-app/fixtures.json`,
  plus spec Test 1), so both arms run exactly the same tasks and no planning call is made.

  | #   | Prompt                                                                        | Tasks (complexity) |
  | --- | ----------------------------------------------------------------------------- | ------------------ |
  | 1   | Change the page title to HELLO WORLD and update the primary button to purple. | 2 (low, low)       |
  | 2   | Rename the --brand CSS variable to --accent in the theme.                     | 1 (low)            |
  | 3   | Fix the paging bug in paginate().                                             | 1 (medium)         |
  | 4   | Add a slugify helper.                                                         | 1 (low)            |
  | 5   | Add a strict parseDuration helper.                                            | 1 (medium)         |
  | 6   | Add a per-key token-bucket rate limiter.                                      | 1 (high)           |

- **Arms.** _routed_: the bench app's config as is, so soot uses the auto models from the
  keys that are set (ADR-043) with the Balanced policy. _baseline_: a models file holding
  only the most expensive model in that pool (highest list output price), `tier: high`,
  `"autoModels": false`. With `XAI_API_KEY` and `DEEPSEEK_API_KEY` set, the pool was
  `deepseek/deepseek-flash` ($0.30 in / $1.20 out per MTok), `xai/grok-build-0.1` ($1/$2),
  `xai/grok-4.3` ($1.25/$2.50), `deepseek/deepseek-v4-pro` ($1.32/$3.96) and `xai/grok-4.7`
  ($2/$6). The baseline was `xai/grok-4.7`.
- **Runner:** `soot run "<prompt>" --agent api --apply --json`, one prompt at a time, on a
  fresh copy of the bench app with a fresh data dir (no routing history). The arm that goes
  first alternates per prompt and repetition.
- **Pass/fail:** after the run, the script runs the task's acceptance tests
  (`examples/bench-app/acceptance/`, protected from edits, never sent to the model) and the
  project tests on the working tree soot landed. Pass means all of them passed.
- **Cost:** soot's actual cost: provider-reported input and output tokens times the list
  price in soot's catalog (checked 2026-11-13). These are not invoice amounts. An attempt
  that reports no usage (a timeout) makes the run's cost unknown, never zero.
- **Wall time:** the whole `soot run` process, including soot's own checks (well under a
  second per task).
- **Runs:** three repetitions, in two invocations: `--reps 1` then `--reps 2`, both on
  2026-11-14 between about 12:44 PM and 1:33 PM PT, with soot built from `5dfbd8d`. Other
  live soot runs (the acceptance runs) shared the same keys during the second invocation.
  After rebasing onto `dd6ff34` (partial edits, ADR-048), a smoke run of prompt 2 in both
  arms passed ($0.0005 routed, $0.0032 baseline); the full set was not re-run.

## What the data shows

- **Light and medium tasks cost less when routed.** On prompts 2 to 5 every run passed in
  both arms, and routed cost was 3 to 10 times lower per prompt (largest on the low tasks
  that went to `deepseek-flash`, smallest on the medium tasks that went to `grok-4.3`).
- **Routing did not save anything on the high task.** Prompt 6 is high complexity. No
  model in this pool is high tier, so routing used the strongest one, `grok-4.7`, the same
  model as the baseline. Every attempt in both arms hit the 120 s per-call limit
  (`modelCallTimeoutMs` default, ADR-040) and reported no usage, so cost is unknown and both
  arms failed 0/3. This prompt says nothing about routing versus the baseline.
- **Prompt 1 favours routing for a reason that is not price.** The title acceptance test
  wants both `<title>` and `<h1>` to read HELLO WORLD. Models often changed only one. A
  retry is told only `acceptance:title failed (exit 1)`, not the test output, and starts
  from a reset worktree. The routed arm recovered by escalating from `deepseek-flash` to
  `grok-4.3` (a different model tried again). The baseline has nowhere to escalate, used up
  its attempts on `grok-4.7` and failed 3/3 (the button task passed each time). So the 3/3
  versus 0/3 is mostly about the escalation path and the missing failure detail. It does not
  show that cheaper models are better at this task. Passing the failed check's output to the
  retry is a follow-up worth doing for both arms.
- **The baseline was slower.** `grok-4.7` took longer per call than `deepseek-flash` and
  `grok-4.3`. Two baseline slugify runs took 119 s and 174 s; the second included a call that
  timed out with no usage reported, so its cost is unknown.

## Caveats

- Small sample: 6 prompts, 7 tasks, 3 repetitions, 2 vendors (xAI and DeepSeek), one day.
  There is no confidence interval worth stating.
- The task set was written for this benchmark, with precise instructions. Real prompts are
  vaguer, and real decomposition (a planning call) would add cost to both arms equally.
- "Most expensive" is by list output price within the keys that were set. With Anthropic or
  OpenAI keys, the baseline would be a different and pricier model.
- Costs are list-price computations from reported tokens, not invoices. DeepSeek prices are
  peak rates. Unknown-cost attempts (13 calls that timed out: 12 on prompt 6, one baseline
  slugify call) are excluded from cost totals; if xAI billed them, the true cost of both arms
  is higher by the same order of magnitude for prompt 6.
- Wall times depend on provider load at the time. Some acceptance runs used the same keys
  during repetitions 2 and 3.
- Pass/fail is the bench app's own tests. Code quality beyond those tests was not reviewed.

## Reproduce

```sh
pnpm install && pnpm run build
export XAI_API_KEY=... DEEPSEEK_API_KEY=...   # your own keys; this spends money
node scripts/benchmark.mjs --live --reps 3 --max-usd 1 --out bench-results.json
```

The script refuses to start without `--live` and when `CI` is set. CI never runs it.
`--only 2,3` runs a subset (for smoke runs), and `--max-usd` stops before the next run once
the known spend reaches that amount.
